When publishing or editing any user-facing "Nice to Have's" list
(README sections, roadmap pages, help text, etc.), always include
introductory text making clear the items are polish/refinement
ideas, not bugs. The app works correctly today; none of the items
block normal use; funds are never at risk from anything on the list.

**Why:** A casual reader scanning the README can otherwise
mis-read the table as a list of open defects, which damages trust
in an app whose core value proposition is fund safety. User raised
this against the initial Road Map publication on 2026-04-29 and
asked that the clarification be applied every time, not just once.

**How to apply:**

- Apply on creation of any new nice-to-have list/section, not only
  when prompted.
- Match the existing wording where reasonable: "polish and
  refinement ideas, not bugs … funds are never at risk from any
  item on this list."
- This rule does NOT apply to the **Possible Major New Features**
  list — those are clearly forward-looking and don't read as bugs.
- This rule does NOT apply to internal memory files / engineering
  notes — only to user-facing docs.
